# Gagarin Avenue WMS

Система складского учёта строительных материалов: приход от поставщиков,
расход в блоки стройки и возврат на склад — с ценами, суммами и полной
историей движения каждой единицы материала.

Интерфейс на двух языках: русский и узбекский.

## Запуск

Нужна база PostgreSQL. Локально подойдёт установленный Postgres, для
рабочего размещения — любой облачный (например, [Neon](https://neon.tech)).

```bash
npm install                    # заодно выполнит prisma generate
cp .env.example .env           # и укажите свой DATABASE_URL
npm run db:migrate             # применить миграции Prisma
npm run db:seed                # заполнить демонстрационными данными
npm run dev                    # http://localhost:3000
```

## Как устроен учёт

Материал проходит замкнутый цикл, и каждый шаг фиксируется в журнале движений:

```
Поставщик ──RECEIPT (приход)──▶ Склад ──ISSUE (расход)──▶ Блок A–E
                                  ▲                          │
                                  └────── RETURN ────────────┘
```

| Операция  | Остаток склада | Числится за блоком |
|-----------|----------------|--------------------|
| `RECEIPT` | `+ количество` | —                  |
| `ISSUE`   | `− количество` | `+ количество`     |
| `RETURN`  | `+ количество` | `− количество`     |

Расходом считается сама выдача в блок: материал уходит со склада на участок
и там расходуется. Отдельной операции «использование» нет — вместо неё за
блоком числится всё, что ему выдали и что он не вернул.

**Журнал движений первичен.** Таблица `stock_movements` только пополняется —
записи никогда не изменяются и не удаляются. Остатки в `materials.quantity` и
`block_stock.quantity` — производные значения, которые меняются исключительно
в одной транзакции с записью движения. Поэтому в любой момент выполняется
равенство:

```
остаток материала = СУММА(warehouse_delta) по всем его движениям
```

Проверить это можно командой `npm run db:check`.

### Цены и суммы

У материала есть текущая цена; в каждой операции сохраняется своя цена за
единицу и сумма строки (`количество × цена`). Сумма считается на сервере и
показывается в форме ещё до сохранения — как в бумажной накладной.

Цену можно менять: вручную в списке материалов и в карточке, а приход с новой
ценой обновляет её сам. **Уже проведённые операции при этом не пересчитываются** —
их суммы зафиксированы в журнале, иначе прошлые накладные «плыли» бы задним
числом. История цен по каждому материалу видна в его карточке.

### Реквизиты накладной

Приход и расход хранят поля бумажной фактуры: дату, номер фактуры, номер машины,
поставщика (откуда), организацию (кому), наименование, единицу, количество,
цену, сумму и способ оплаты — наличные или перечисление.

### Защита от некорректных данных

Правила закреплены на трёх уровнях, а не только в интерфейсе:

1. **Ограничения базы** — `CHECK (quantity > 0)`, `CHECK (quantity >= 0)` для
   остатков и цен, внешние ключи. Отрицательный остаток невозможен физически.
2. **Транзакции** — операция выполняется в `BEGIN IMMEDIATE`, поэтому проверка
   остатка и его изменение неделимы. Два одновременных пользователя не могут
   выдать один и тот же материал дважды.
3. **Серверная валидация** — каждый server action проверяет права доступа и
   разбирает данные схемой Zod, независимо от проверок в браузере.

## Языки интерфейса

Переключатель языка есть в верхней панели и в разделе «Настройки».
Выбор сохраняется в cookie браузера, отдельных адресов вида `/ru` и `/uz` нет.

Работает на [next-intl](https://next-intl.dev). Сообщения лежат в
[`messages/`](messages/) в формате ICU: множественное число русского языка
(«1 позиция / 2 позиции / 5 позиций») берётся из стандарта, а не считается кодом.

Русский файл задаёт форму ключей — он объявлен как тип сообщений в
[`next-intl.d.ts`](next-intl.d.ts), поэтому **обращение к несуществующему ключу
перевода не даст проекту собраться**. Чтобы добавить язык, положите файл рядом
с `uz.json` и добавьте код в `LOCALES`.

Категории, единицы измерения и причины возврата хранятся в базе по-русски —
это их постоянные ключи. Переводятся они только при показе, поэтому смена
языка не затрагивает данные и историю операций. Поиск по материалам ищет и по
исходному значению, и по переводу: единица хранится как «шт», а найти её можно
и по «dona».

## Роли

- **Администратор** — все операции, справочники, организации, сотрудники,
  отчёты, настройки.
- **Работник склада** — приход, расход, возврат, просмотр склада, материалы
  с ценами, блоки, поставщики и отчёты. Без доступа к организациям,
  сотрудникам и настройкам.

## Технологии

Next.js 16 (App Router, Server Actions) · React 19 · TypeScript · Tailwind CSS 4 ·
shadcn/ui на Base UI · next-intl · Prisma 7 + PostgreSQL.

Схема базы описана в [`prisma/schema.prisma`](prisma/schema.prisma). Простые
выборки идут через модели Prisma, сводные отчёты — через `$queryRaw`: агрегаты
вида «сумма по типу операции в разрезе материала» в SQL выражаются одним
запросом.

CHECK-ограничения (остаток не меньше нуля, количество строго больше нуля)
Prisma в схеме не выражает, поэтому они заданы SQL-ом в миграции
`integrity_checks` — без них отрицательный остаток был бы защищён только
кодом приложения.

### Переменные окружения

| Переменная         | По умолчанию    | Назначение                                      |
|--------------------|-----------------|-------------------------------------------------|
| `DATABASE_URL`     | —               | Подключение приложения (у Neon — адрес с `-pooler`) |
| `DIRECT_URL`       | —               | Прямое подключение для миграций (без `-pooler`)  |
| `WMS_DB_POOL_MAX`  | `5`             | Размер пула подключений на экземпляр             |
| `WMS_TIMEZONE`     | `Asia/Tashkent` | Часовой пояс для показа дат                      |

Пулер Neon работает в transaction-режиме и не поддерживает операции, которые
выполняет `prisma migrate`, поэтому адреса для приложения и для миграций разные.

## Размещение на Vercel

```bash
# 1. Создайте базу в Neon и скопируйте POOLED connection string
#    (в адресе есть «-pooler»)

# 2. Примените схему и заведите администратора — с локальной машины:
export DATABASE_URL="postgresql://...-pooler.../neondb?sslmode=require"
npm run db:migrate
npm run db:create-admin -- admin "надёжный-пароль" "Иван Иванов"

# По желанию — демонстрационные данные (материалы, бригады, история):
npm run db:seed

# 3. В Vercel → Settings → Environment Variables добавьте DATABASE_URL
#    с тем же значением, затем Deploy.
```

Схема намеренно не применяется при запуске приложения: на serverless-платформе
холодный старт происходит часто, и миграция на каждом из них была бы медленной
и небезопасной при параллельных запусках. `db:migrate` запускается отдельно.

## Выгрузка данных

Отчёты и любые таблицы операций выгружаются в Excel (`.xlsx`) и CSV из реальных
данных: остатки с ценами и стоимостью, расход по блокам, закупки у поставщиков
с разбивкой на наличные и перечисление.

## Обмен с 1С

Загрузка данных из 1С подготовлена, но ещё не включена: у материалов,
поставщиков, организаций, блоков и операций есть поле `external_id` под код 1С,
по которому импорт узнаёт уже заведённые записи и не создаёт дублей. Контракт
данных описан в [`src/server/integration/onec.ts`](src/server/integration/onec.ts),
соответствие полей и что нужно от администратора 1С —
в [`docs/1c-import.md`](docs/1c-import.md).
